# 静态改写

静态改写是把 Android 的机器码变成 iOS 肯装载、肯执行的代码的办法。
“静态”是指它发生在构建机上、App 签名之前；手机上不做任何翻译。

改写器是 [`experiments/g0/e3/rewrite.py`](../../experiments/g0/e3/rewrite.py)，约 580 行 Python。
把它用到整个 Android 镜像上的驱动脚本是 [`tools/build-native-code.py`](../../tools/build-native-code.py)。
运行时一侧是 [`runtime/NativeCode.cpp`](../../runtime/NativeCode.cpp) 和 [`runtime/NativeEntry.S`](../../runtime/NativeEntry.S)。

## 为什么要保留寄存器

客体和宿主都是 ARM64，所以大多数客体指令可以原样执行。
不能原样保留的，是一切依赖“东西在哪里”的指令：客体指针不是宿主指针，客体的代码地址不是翻译所在的位置，`svc` 也不能真的落到 iOS 内核里。
这样的指令都要换成一小段指令序列，而序列需要工作空间：至少要有指向线程状态的指针、指向内存表的指针、指向代码表的指针，外加一个暂存寄存器。

如果客体自己的代码把所有寄存器都用上了，改写器就得在每段序列前后保存和恢复寄存器，或者逐个函数分析哪个寄存器空闲。
这里换了个做法：编译客体时就让它永远不用运行时需要的寄存器。
Android 的 C、C++ 和汇编用下面的参数构建：

```
-ffixed-x18 -ffixed-x25 -ffixed-x26 -ffixed-x27 -ffixed-x28
```

Rust 用对应的 `+reserve-x…` 目标特性（[`experiments/aosp/patch.py`](../../experiments/aosp/patch.py)）。
少用这几个寄存器的代价，在一组命令行基准上测不出来（在参考内核上耗时之比为 1.003）。

预编译好的 Android 镜像不能直接用：原版 Android 17 SDK 镜像里约 6% 的指令用到了 `x25` 到 `x28`。
`x18` 在那里几乎没人用，但它也帮不了运行时，因为 iOS 每次进入内核都把它清零，纯计算期间线程被抢占时也会清零（见 [design-notes.md](design-notes.md)）。
保留它只是为了让客体代码不依赖它。

只加编译参数还不够。补丁脚本还改了这些地方：

- Bionic 的 `setjmp`/`longjmp`，不再保存和恢复 `x25` 到 `x28`（`fork` 之后，保存下来的值是父进程的）；
- ART：编译器不分配这几个寄存器，调用约定里不再列出它们，手写的入口代码不再恢复它们；ART 的汇编解释器（nterp）关闭，改用可移植的那个；
- 带手写汇编且用到这些寄存器的库（BoringSSL、Cronet 里自带的两份 BoringSSL、TensorFlow Lite 的一部分、ruy），改用它们的 C 或 C++ 实现；
- 工具链自带的预编译运行时库（compiler-rt builtins、libunwind、libc++、最小版 UBSan 运行时），由 [`experiments/aosp/build-runtimes.sh`](../../experiments/aosp/build-runtimes.sh) 用同样的参数重新编译。

[`experiments/aosp/audit.py`](../../experiments/aosp/audit.py) 反汇编构建出来的目录树，列出仍然点名使用保留寄存器的文件。

## 寄存器的分工

| 寄存器 | 在改写后代码里的作用 |
| --- | --- |
| `x25` | 当前客体线程的上下文（`NativeCode.cpp` 里的 `NativeContext`）：保存的寄存器、线程指针、运行时的入口地址。 |
| `x26` | 代码表，带偏置，使客体地址 `pc` 的表项位于 `x26 + 2 * pc`。每个表项是该指令翻译的宿主地址。 |
| `x27` | 进程的内存表：客体地址空间里每一块对应一个 8 字节的偏移。 |
| `x28` | 暂存。存放正在计算的宿主地址，或间接跳转的目标。 |
| `x18` | 客体和运行时都不用。 |
| `sp` | **宿主**地址。 |
| 其余 | 客体的值，和原程序里一模一样。其中的指针是客体地址。 |

让 `sp` 保持为宿主地址，相对栈指针的访存（约占全部指令的十分之一）就完全不用改写。
一个线程的栈总是落在偏移相同的若干块里，所以对 `sp` 做加减仍然成立。
程序把 `sp` 复制到别的寄存器或复制回来时，改写器在宿主地址和客体地址之间做转换。

## 改写器对一个 ELF 文件做什么

改写器读出 ELF 文件里唯一的可执行段，每四个字节走一步。
对每条客体指令，它输出一个标号和零条或多条宿主指令。
改写器文件头的说明如下：

```
loads and stores through a register other than sp   add the base first
copies between sp and another register              convert between host and guest
adr, adrp, literal loads                            use the guest address as a constant
svc                                                 enter the runtime
mrs/msr tpidr_el0                                   use the context
br, blr, ret                                        translate the guest pc through the table
```

其余指令原样复制；指针认证的 hint 指令换成 `nop`。
夹在代码段里、解码不成指令的数据，按原始的字复制。

**访存。**
经寄存器 `xN` 的读写，先在 `x28` 里算出宿主地址，再经 `x28` 做原来的访问：

```python
self.emit("ubfx x28, x%d, #%d, #%d" % (register, CHUNK_SHIFT, CHUNK_BITS))
self.emit("ldr x28, [x27, x28, lsl #3]")
self.emit("add x28, x28, x%d" % register)
```

第一条从客体地址里取出块号（忽略最高字节，Bionic 在那里放了标签），第二条读出这一块的偏移，第三条加上去。
客体地址是 39 位。发布的构建用 1 MiB 的块（`--chunk-shift 20`）。
带回写的寻址形式（前变址和后变址）被拆开，寄存器的更新放在访问之后；这样出错的访问什么都还没改，可以当作一条客体指令来重试或上报。

打开了两项优化。
`--reuse`：与上一次访问使用同一个基址寄存器时，直接用 `x28` 里还在的宿主地址。
`--split-index`：带寄存器偏移的访问先按基址寄存器所在的块查表（不必等下标算出来），再确认完整地址落在同一块里；不在同一块时，由放在别处的慢路径做完整查表。

**地址。**
`adr` 和 `adrp` 相对程序计数器算地址。翻译里的程序计数器在别处，所以改写器把客体地址作为常量写出来（`movz`/`movk`）。
一份翻译之所以绑定一个装载地址，原因就在这里。

**直接跳转。**
跳到同一模块内的地址，变成跳到目标指令的标号。
翻译后的代码比原来大，条件跳转的目标可能够不着了，这时输出“反条件跳过，加一条无条件跳转”。

## 间接跳转与返回

`br`、`blr` 和 `ret` 跳到寄存器里的地址，那是一个客体代码地址。
翻译要查表：

```python
def lookup(self, register):
    self.emit("add x28, x26, x%d, lsl #1" % register)
    self.emit("ldr x28, [x28]")
```

然后 `br x28`。
代码表里每条 4 字节的客体指令对应一个 8 字节的表项，所以下标是 `2 * pc`。

链接寄存器 `x30` 里保存的是**客体**的返回地址，所以每次返回也要查表。
ART 靠读栈上的返回地址来遍历栈帧，返回地址是客体地址时它在这一点上不用改。
在命令行基准上测得，返回查表比保持原生返回只多约一个百分点。

跳出模块的直接跳转（编译好的 Java 代码就是这样调用另一个文件里的辅助例程的）同样走表，因为要等两个文件都映射好才知道它通向哪里。

控制流正是靠这张表被约束住的。
只有进程把某个模块映射到了它的地址上，内核层才把该模块在表里的那一段映射进来。
其余部分只是保留的地址空间，后面什么都没有，所以跳往没有翻译的地址时，在查表这一步就出错，控制流还没去任何地方，运行时就接手了。
模块内部不是指令的地址，通向一段离开原生代码的桩。

## 系统调用

```python
if w & 0xFFE0001F == 0xD4000001:  # svc
    self.emit("adr x28, 1f")
    self.emit("b _guest_svc")
    self.out.append("1:")
```

`_guest_svc` 是链接进每个 framework 的两条指令。它从上下文里取出运行时的入口并跳过去：

```
_guest_svc:
	ldr x27, [x25, #864]
	br x27
```

要经过上下文，是因为两个 Mach-O 镜像之间的调用否则会经过链接器生成的桩，而那段桩会用到属于客体的寄存器。
这里可以借用 `x27`，因为每次进入客体时运行时都会重新装入它。
入口是 `NativeEntry.S` 里的 `nestvane_native_svc`，它把所有客体寄存器存进上下文，以 `x28` 作为恢复执行的位置，然后回到主循环。
对线程指针（`tpidr_el0`）的读写，变成对上下文的读写。

## 为什么翻译绑定装载地址，地址又怎样分配

客体地址作为常量写进了翻译，又作为位置体现在代码表里，所以模块必须装在翻译时设定的地址上。
Android 平常是把库装到随机地址的。
让地址固定下来靠三件事。

1. `build-native-code.py` 在 `0x8000_0000` 到 `0xFFF0_0000` 的范围里给每个文件分配一个地址，记在 `generated/native-code/addresses.txt` 里。文件在多次构建之间保持地址不变，增删文件不会迫使其余文件全部重新翻译。地址按 256 KiB 对齐，因为 Bionic 的控制流完整性（CFI）影子表每 256 KiB 一项，两个库不能落在同一项里。
2. 文件按内容识别，不按路径或 inode：标识是文件前 16 KiB 的 FNV-1a 哈希，再混入文件长度。客体映射文件时，运行时算出同样的标识。
3. 动态链接器打了补丁，会去问文件该放在哪里。内核层在辅助向量里多放两项（`0x4e56`、`0x4e57`），给出一张“设备号、inode、地址”的表；文件在表里时，链接器就保留那个地址。在真实的 Linux 内核上没有这两项，链接器的行为和原版一样，所以同一份镜像也能在参考模拟器里开机。

启动类路径的编译产物（`boot*.oat`）按它的镜像文件头里记录的地址翻译，ART 以 `-Xnorelocate` 启动，把文件映射到那里。

一个进程可能把同样的字节装两次：内容相同而路径不同的库、在应用的链接器命名空间里再装一遍的平台库，或者 zygote 已经装过、`system_server` 又装一遍的编译产物。
一份翻译只对应一个地址，所以这类文件另有一份放在别的地址上的备用翻译，内核层把进程里还没用过的那一份分出去。

## 打包

每份翻译由 Apple 的工具链汇编成目标文件。
一个 Mach-O 镜像装不下全部，所以目标文件按大小分进 12 个动态库；在 iOS 上每个库包成一个 framework，即 `NestvaneCode<n>.framework`，因为 App 里不能带裸的动态库。
`modules.c` 列出每个模块的标识、大小、地址和名字。

每条客体指令 8 字节的代码表会和代码本身一样大。
所以 framework 里带的是紧凑形式（`--final-table`）：每条指令的翻译长度占 2 字节，每 64 条指令记一个起点，再加上经入口桩进入的指令列表。
运行时据此生成真正的表，一次一页，在某页第一次被查到时生成。
这些页属于一个文件，iOS 可以把它们写回并收走，它们不计入 App 自身的内存占用。

带 `--used <清单>` 时，驱动脚本不再打包某次记录下来的会话里从未映射过的备用副本，以及客体没有对应硬件的模块（蓝牙、Wi-Fi、NFC 等）。
没有翻译的文件照样能运行：解释执行。

## 没有翻译的代码：混合执行

不是所有代码都能事先翻译：用户安装的 APK 里的原生库，在构建 App 时并不知道。
这类代码由 [`runtime/AArch64.cpp`](../../runtime/AArch64.cpp) 在原地解释，并且和翻译过的代码在同一个进程里。

内核层把动态链接器给未翻译的库做的地址保留，放进一段固定的 1 GiB 客体地址范围（[`runtime/NativeCode.hpp`](../../runtime/NativeCode.hpp) 里的 `foreignLow` 到 `foreignHigh`）。
代码表覆盖这段范围，但里面没有任何表项。
翻译过的代码调用这样的库时，查表出错；运行时接住这个故障，解释器从目标地址开始执行，直到控制流回到一个有翻译的地址，再恢复原生执行。

单条指令也用同一套机制。
如果一条翻译过的指令在宿主上出错（它访问的内存还没有宿主页，或者访问越出了一段连续的块），客体寄存器仍是这条指令执行前的值，解释器只执行这一条，然后从下一条继续原生执行。

原生代码停下来的原因，就是 `NativeCode.hpp` 里的 `Exit` 枚举：`syscall`、`fault`、`preempted`、`interpret`、`retry` 和 `lost`。
如果程序本身或它的动态链接器没有翻译，整个进程都解释执行，因为翻译过的库返回到它里面时会查不到表项。

解释执行比翻译后的代码慢得多，[status.md](status.md) 里有一个例子。

## 实测的代价

数字都出自 [`results/G0.md`](../../results/G0.md)。

| 测量 | 结果 |
| --- | --- |
| 改写后的 Bionic 工具，对比同一批二进制在 Linux 内核上的耗时（Mac） | 原生的 1.07 到 1.6 倍 |
