# G0 前提实验

对应 [REVIEW.md](../REVIEW.md) 5.3 节的五个实验，全部完成。验收设备是 iPhone 15 Pro，iPhone 11 作为低配对照。

- **设备**：iPhone 15 Pro（iPhone16,1，A17 Pro，8 GB，iOS 26.2）和 iPhone 11（iPhone12,1，A13，4 GB，iOS 26.0.1）。Xcode 27.2，最低系统版本 iOS 26。
- **构建**：`experiments/g0`，Release 配置，开发签名（带 `get-task-allow`）。由 `devicectl` 启动，报告中 `traced=0`，即没有调试器附加。
- **复现**：`G0_TEAM=<团队> experiments/g0/run.sh <UDID> <G0|G0Extended|G0Code|G0Guest> <探针>`。E3 先运行 `experiments/g0/e3/build.sh`。
- **原始报告**：本目录下的 `g0-*.txt`。

## 结论

| 实验 | 结果 | 对设计的影响 |
| --- | --- | --- |
| E1 地址空间 | 无权限约 7 GiB，带 Extended Virtual Addressing 约 53 GiB，两台设备相同 | 该权限是硬依赖。53 GiB 要分给所有客体进程 |
| E2 写时复制重映射 | 正确，256 MiB 驻留 5–12 ms | fork 可以这样做 |
| E3 保留寄存器加改写 | 从 AOSP 源码带保留寄存器构建的 Bionic、linker64、mksh 和 toybox，改写后在 Mac 和 iPhone 15 Pro 上原生运行，与参考内核输出一致，开销为原生的 1.07–1.6 倍 | 路线成立。ART 已打补丁，还没有运行过 |
| E4 进程内故障恢复 | 每种情形 100,000 次全部恢复，平均 1.5–2.6 µs | ART 的隐式检查可以保留 |
| E5 签名代码装载 | 512 MiB 的 dlopen 合计 8–105 ms，首次触碰 0.24–1.37 秒 | 装载成本不构成障碍 |

实验中新发现的四件事：

- **「每进程一段连续内存」放不下原版 Android。** Android 17 参考镜像的 117 个进程共保留 1,510.7 GiB 地址，iOS 只有 53 GiB。客体地址要按块查表翻译，见「地址保留和查表翻译」。
- **查表翻译可以承受。** 同一组基准上是原生的 1.31 倍，基址方案是 1.16 倍。
- **预编译的 Android 镜像不能直接改写。** 它的代码有约 6% 的指令用到 x25–x28，唯一空闲的 x18 在 iOS 上保不住。要从源码带保留寄存器重编，或者在二进制层面逐处找空闲寄存器。
- **共享匿名页重复计入内存占用。** iOS 按映射计数，Android 17 参考镜像上估算是去重后的 1.8 倍。把 Zygote 的内存放在文件后备的共享映射上可以消除，已在真机验证。

## E1 地址空间

| | iPhone 15 Pro 无权限 | iPhone 15 Pro 带权限 | iPhone 11 无权限 | iPhone 11 带权限 |
| --- | --- | --- | --- | --- |
| `vm_map` 上限 | `0x458000000` | `0xfc0000000` | `0x458000000` | `0xfc0000000` |
| 累计可保留 | 7.141 GiB | 52.812 GiB | 7.266 GiB | 52.859 GiB |
| 最大单块 | 4 GiB | 32 GiB | 4 GiB | 32 GiB |
| 可用内存 | 3,370 MiB | 6,138 MiB | 2,093 MiB | 2,343 MiB |

「带权限」指同时有 Extended Virtual Addressing 和 Increased Memory Limit。

- 地址空间上限与机型和内存大小无关，都是 `0xfc0000000`。内存上限差别很大。
- 保留地址本身不增加内存占用。自动签名直接拿到了两项权限。
- 53 GiB 是全部客体进程共用的预算。

### 地址保留和查表翻译

Android 17 参考镜像到 Launcher 时各进程的 `/proc/<pid>/maps`（`g0-address-space-api37-default.txt`）：

| | 数值 |
| --- | --- |
| 进程数 | 117 |
| 保留地址合计 | 1,510.7 GiB |
| 其中 `PROT_NONE` | 1,375.0 GiB |
| 其余（可读写，多数从未触碰） | 135.8 GiB |
| 最小的原生进程 | 约 10.3 GiB |
| `system_server` | 21.9 GiB |

- 每个进程都有约 8 GiB 的 Scudo 保留和 2 GiB 的 CFI shadow，ART 进程另有两块 1 GiB 的 LinearAlloc。
- 即使只算非 `PROT_NONE` 的部分也有 135.8 GiB，是 iOS 上限的 2.6 倍。给每个进程保留一整段连续内存的做法对原版镜像不成立。
- 可行的做法是把客体地址按块翻译：宿主地址 = 客体地址 + 表[客体地址 >> 24]。只有真正被触碰的块才占宿主地址，`PROT_NONE` 保留不占。

查表翻译的代价用 E3 的同一套程序测了（`rewrite.py --table`，16 MiB 一块，每次访存多 3 条指令，其中一条是读表）：

| | 基址寄存器 | 查表 |
| --- | --- | --- |
| 静态膨胀 | 1.40 倍 | 1.72 倍 |
| 相对 Linux 原生，几何平均 | 1.16 倍 | 1.31 倍 |
| 最差一项 | 1.37 倍 | 1.62 倍 |
| 与参考内核输出一致 | 20 / 20 | 20 / 20 |

- 两列都是返回地址保持为客体地址的模式。这次测量里所有块都落在同一段内存里，测的只是指令开销。稀疏布局的实现和实测见下一节。
- 单条访存可以改用寄存器偏移寻址省掉一条指令，这里没有做。

### 稀疏地址空间的实现

上一节的方案已经在 E3 的运行时里实现（`runtime.c` 的 `-DSPARSE`，配合 `rewrite.py --table`），客体有 39 位地址空间：

- 客体内存按块（默认 16 MiB，可调）管理，每块有自己到宿主内存的偏移。相邻的块尽量拿相邻的宿主地址，连成一段（run），每段前后各留保护页。
- 没有宿主内存的块，偏移指向宿主映射不到的高地址（2^47 以上）。访问它必然出错，出错地址减去偏移就是客体地址，所以空指针检查、栈溢出保护页这类客体自己的故障照常变成 SIGSEGV。
- `PROT_NONE` 保留和 32 MiB 以上的匿名映射先只记在表里，`mprotect` 成可访问或第一次被碰到时才给这一块宿主内存。Scudo 的 8 GiB 保留因此不占宿主地址。
- 立即数偏移的访存按基址寄存器所在的块查表。偏移跨出这一段时落在保护页或空洞里，由故障处理程序解码这条指令、逐字节完成访问，再从下一条指令继续。寄存器偏移的访存能跨任意远，所以按完整地址查表，多两条指令。
- 线程的栈整体放在一段里（32 MiB 以下的映射在分配时保证这一点），所以 `sp` 仍是宿主地址，栈上访问和 `sp` 加减都不改写。写 `sp` 时把所在段的偏移记进上下文，读 `sp` 时减回去。
- fork 逐段做写时复制的 `vm_remap`，三张表（偏移、已映射位图、保护位）是一块内存，同样写时复制。
- 读写系统调用的缓冲区可能不连续，按段拆成 `readv`/`writev`。`mremap` 支持 `MREMAP_FIXED` 和 `MREMAP_DONTUNMAP`，ART 的压缩式 GC 每轮都用。

- gzip 这类以数组下标寻址为主的代码最吃亏：查表依赖下标，每次访存的地址计算多出约 7 个周期的依赖链。`rewrite.py --split-index` 改成先按基址寄存器查表（不依赖下标，处理器可以提前算好），再用不改标志位的 `eor`/`ubfx`/`cbnz` 确认地址和基址在同一块，不在同一块才跳到按完整地址查表的慢路径。1 MiB 一块时 gzip 从 403 ms 降到 273 ms（整段模式是 238 ms），其余各项变化在 ±5% 内，28 个脚本的输出不变。
- ART 的解释器在稀疏模式下仍比整段模式慢约 1.4 倍，它的访存多是基址不断变化的立即数偏移，每次都要查表，上面两项优化帮不上。
- 乘上整段模式相对原生的 1.16 倍，稀疏模式约为原生的 1.4–1.5 倍，比上一节用单段内存估的 1.31 倍高。
- 可选的优化（`rewrite.py --reuse`）：同一基址寄存器的连续访问复用上一次查表的结果。宿主不支持只执行的代码页（在 Mac 上测过，`PROT_EXEC` 的页仍然可读），不能靠故障兜底，所以给复用区间里的每条指令生成一个重新查表的入口桩，代码表指向桩，间接跳转和信号返回都从桩进入。libc 里约 20% 的访存能复用。1 MiB 一块时 28 个脚本的输出不变，gzip 快 10%，sed、grep 快约 5%，其余持平。默认没有打开。

**类预加载**：`guest-tests/Preload.java` 按 AOSP 的 `preloaded-classes` 列表逐个 `Class.forName`，和 zygote 启动时做的一样。18,784 个类里 18,228 个加载成功，Mac 上整段模式 67 ms，稀疏模式 95 ms。它们已经在启动镜像里初始化好，预加载只是查表。另外 246 个不在这棵树的启动类路径里，310 个的静态初始化要调用框架的本地方法，`dalvikvm` 没有注册这些方法（要用 `app_process`，等完整镜像）。

- 第一次跑时 zygote 死在预加载 `libhttpengine.so`：它带着 Cronet 自己的一份 BoringSSL 汇编（用 x25–x28），加载时自检就会破坏运行时的寄存器。关掉这份汇编重新构建后，预加载完整跑完（上面两张表是修好之前量的，停在兼容性配置之后；修好之后 Mac 上 `ZygotePreload` 110 ms，`ZygoteInit` 共 131 ms）。
- 接着 zygote 进入 `Accepting command socket connections`。加上 `--start-system-server` 后它 fork 出 system_server：子进程完成降权、调度策略、SELinux 上下文（这里是接受并忽略），改名为 system_server，装载连接模块的 JNI 库，然后在打开 `/dev/binder` 时终止。E3 的运行时没有 Binder，这就是它能走到的最远处。

**放到参考模拟器里启动**（Mac 上的 Android 模拟器，真实的 ARM64 Linux 内核，16 KiB 页）：第一次没有开机，zygote 每 5 秒重启一次。原因是链接器补丁里用来询问装载地址的私有系统调用：真实内核上 system_server 和各媒体服务带 seccomp 过滤器，陌生的系统调用直接被 SIGSYS 杀掉。在我们自己的运行时里没有 seccomp，所以之前没有暴露。补丁改成不走系统调用：运行时在辅助向量（auxv）里给出一张「设备号、inode、装载地址」表，链接器查表；真实内核上没有这两项，行为和原版一样。

| 阶段 | 内核启动后的时间 |
| --- | --- |
| zygote 开始 | 1.42 s |
| 预加载结束 | 1.95 s（`ZygotePreload` 222 ms） |
| system_server 开始运行 | 2.05 s |
| 包管理就绪 | 2.47 s |
| AMS 就绪 | 4.26 s |
| 开机动画结束 | 5.92 s |
| Launcher 显示 | 6.84 s |

- 也就是说，保留五个寄存器、关掉这些汇编内核、全量 AOT 之后，系统本身在 Mac 上 6.8 秒到桌面。这是改写路线的参照：改写后的代码约为原生的 1.4–1.5 倍，iPhone 15 Pro 的单核比这台 Mac 慢，内核层的开销另算。
- zygote 预加载这一段，改写后在 Mac 上是 110–220 ms，和这里原生的 222 ms 在同一量级。

`experiments/aosp/audit.py` 逐个反汇编树里的 ELF，列出还在使用 x25–x28 的文件。目前剩下的是 ASan 运行时（不加载）、`libsimpleperf_profcollect.so`（还没看）和 ART 里已停用的 nterp。

全量 AOT 之后启动镜像的 oat 共 126 MB（按 profile 编译时 framework 这一块约 11 MB，现在 70 MB），system_server 和各 APEX 的 odex 共 106 MB。

**没有 JIT 时启动镜像必须全量编译**：`Bench.java` 里 `Arrays.sort(int[])` 排 400 万个整数用了 2.1 秒，是解释执行的速度。启动镜像按 profile 编译，没进 profile 的方法在真机上靠 JIT 补，这里没有 JIT，只能走 switch 解释器。启动镜像、system_server 和预装应用都要用 `speed` 过滤器全量编译，oat 会变大，这部分体积还没有量。

### x18 能否使用

预编译镜像里 x18 几乎没有被使用，如果能拿来用就不必重编。在两台设备上向 x18 写入一个值后反复读回（各 1.5 秒）：

| 期间做的事 | iPhone 15 Pro 丢失 | iPhone 11 丢失 |
| --- | --- | --- |
| 纯计算 | 941 / 55,117 | 790 / 32,813 |
| 系统调用 | 每次 | 每次 |
| 睡眠、让出 CPU | 每次 | 每次 |
| 信号 | 每次 | 每次 |
| 缺页 | 17,632 / 1.6 亿 | 22,083 / 5,600 万 |

丢失后读到的都是 0。内核在每次进出时清零 x18，纯计算期间被抢占也会丢。它连只跨两条指令的暂存都不能当。

## E2 `vm_remap` 写时复制

| 项目 | iPhone 15 Pro | iPhone 11 |
| --- | --- | --- |
| 重映射 1 GiB 区域，驻留 64 / 256 MiB | 2.9 / 7.0 ms | 2.6–2.9 / 11.9–12.1 ms |
| 重映射 2 GiB 区域，驻留 256 / 512 MiB | 4.9 / 16.2 ms | 10.6 / 21.1–25.4 ms |
| 65,536 个交替保护的映射项（1 GiB） | 27.6 ms | 39.9–42.7 ms |
| 子映射读缺页，每页 | 0.6–0.9 µs | 约 0.7 µs |
| 子映射写时复制，每 16 KiB 页 | 2.6–4.2 µs | 3.2–4.0 µs |
| 连续 12 代重映射，平均 | 0.05 ms | 0.08 ms |

- 父子双向写入互不可见，全部用例 0 处不一致。保护属性在重映射后保留。
- `VM_FLAGS_FIXED | VM_FLAGS_OVERWRITE` 可以把副本放进预先保留的段，子进程的基址可以预先规划。
- 请求 4 KiB 的重映射会复制整个 16 KiB 页，页内 4 KiB 的 `mprotect` 返回 `EINVAL`。直映内存要求客体用 16 KiB 页。
- `MAP_SHARED` 文件映射经复制后不再共享。对该范围再做一次 `copy = FALSE` 的重映射即可恢复 Linux fork 的语义。

### 内存占用的计数方式

256 MiB 驻留，第二个映射只读或写入后的 `phys_footprint`（iPhone 15 Pro，MiB）：

| 后备 | 第二个映射 | 触碰后 | 读后 | 写后 |
| --- | --- | --- | --- | --- |
| 匿名 | 写时复制 | 265.1 | 521.3 | 521.3 |
| 匿名 | 共享 | 265.1 | 521.3 | — |
| 已删除的文件，`MAP_SHARED` | 写时复制 | 9.2 | 9.3 | 265.3 |
| 已删除的文件，`MAP_SHARED` | 共享 | 9.2 | 9.3 | — |

匿名页读后占用翻倍时，整机空闲内存没有变化。翻倍是记账，不是真实复制，但 jetsam 依据的正是这个数。iPhone 11 上数值相同。

### 重复计数的规模和对策

**规模**用参考模拟器估算（`experiments/g0/guest-memory.py`）。采集前关闭了 swap 和应用压缩，内核没有做过页回收，所以每个映射的 `Referenced` 可以近似为「fork 之后碰过的页」。

| 口径 | Android 17 `default`（4 KiB 页，117 个进程） | Android 16 带 Google 应用（16 KiB 页，140 个进程） |
| --- | --- | --- |
| 去重后的匿名内存（`Pss_Anon`） | 570 MiB | 1,320 MiB |
| 碰过的匿名页之和，即 iOS 的计数方式 | 1,037 MiB | 2,593 MiB |
| Linux 的 `RssAnon`，含继承但没碰过的页 | 2,492 MiB | 4,650 MiB |

- 第一列就是 `PLAN.md` 里的参考构建 CE2A.260420.051.A3，到 Launcher 时采集。按 iOS 的方式计数是去重后的 1.8 倍，多出约 470 MiB。
- `Referenced` 也包含页级的引用标记，可能略微高估。这是在参考内核上的估算，不是在 Nestvane 上的实测。
- iPhone 15 Pro 的上限是 6,138 MiB，这个量可以承受。iPhone 11 是 2,343 MiB，需要下面的对策。

**对策**是让 Zygote 把内存建在已删除文件的 `MAP_SHARED` 映射上，子进程仍用写时复制重映射。模型为 48 MiB 的父进程，64 个子进程各读 25%、写 10%：

| 设备 | 匿名后备 | 文件后备 |
| --- | --- | --- |
| iPhone 15 Pro | 826.1 MiB | 317.1 MiB |
| iPhone 11 | 823.5 MiB | 314.4 MiB |

- 文件后备时只有子进程写过的页计入占用。64 个子进程各读完全部 48 MiB，占用只增加约 1.5 MiB。
- 数据全部正确。父进程首次写入每页慢 1–3 µs，子进程的缺页耗时没有明显差别。
- 进程的磁盘写入计数在测试期间和之后 3 秒都是 0。长时间运行后脏页是否回写闪存还没有验证。

## E3 保留寄存器的构建和改写

先用 musl 1.2.5 和 toybox 0.8.12 在本机验证了工具链能否保留寄存器、改写规则是否正确、开销多大，再在构建机上用 AOSP 源码做了 Bionic 的版本，见本节末尾。

**构建**（`experiments/g0/e3/build.sh`）：用 NDK 的 Clang 加 `-ffixed-x18 -ffixed-x25 -ffixed-x26 -ffixed-x27 -ffixed-x28` 编译 musl、compiler-rt 的长双精度函数和 toybox，静态链接。

- toybox 共 142,796 条指令，用到 x25–x28 的只有 `setjmp` 里保存寄存器的 2 条。不保留时是 7,610 条。
- 唯一的源码改动在 musl 的 `longjmp`：不恢复 x25–x28。fork 之后 `jmp_buf` 里存的基址是父进程的。
- NDK 预编译的 compiler-rt 用到了 x25 和 x26，必须重编。任何链接进客体的预编译库都有这个问题。
- 保留四个寄存器的代价测不出来：同一批基准在参考内核上的耗时比是 1.003。

**改写**（`experiments/g0/e3/rewrite.py`）：把 ELF 的代码段转成 Mach-O 汇编，x27 作基址，x28 作暂存，x26 指向代码表，x25 指向线程上下文。寄存器里是客体地址，只有 sp 存宿主地址，这样占 10.6% 的 sp 相对访存不用改。

| 指令类别 | 占比 | 处理 |
| --- | --- | --- |
| 原样复制 | 43.8% | — |
| 直接分支 | 15.2% | 重新链接到新位置 |
| 经寄存器访存 | 13.9% | 先加基址，多 1 条 |
| 经 sp 访存 | 10.6% | 不变 |
| 调用和返回 | 8.2% | 见下 |
| `adr` / `adrp` | 6.0% | 换成客体地址常量 |
| sp 与其他寄存器之间的复制 | 2.0% | 加减基址 |
| `svc`、TLS、间接跳转 | 0.3% | 进运行时或查表 |

- 静态膨胀 1.24 倍。返回地址若保持为客体地址（ART 读栈上的返回地址，需要这样），每次返回都要查表，膨胀 1.40 倍。
- 对 Android 17 预编译的 `libc.so`、`linker64` 和 `libart.so` 只做统计，膨胀是 1.23、1.26 和 1.29 倍。

**运行时**（`experiments/g0/e3/runtime.c`，约 600 行）：每个客体进程一段连续内存和一个宿主线程，fork 用 `vm_remap` 写时复制后只改基址和 sp，exec 原地重装镜像，Linux 系统调用由宿主提供。fork 平均 19 µs。

**正确性**（`experiments/g0/e3/compare.py`）：20 个脚本覆盖 shell 运算、多级管道、命令替换、文件操作、fork 循环、exec 自身、哈希、gzip、sed、bc、sort、find 等。

- 参考是同一个 ELF 在 ARM64 Linux 内核（Android 模拟器）上的输出和退出码。
- Mac 上两种改写模式、不保留寄存器的版本，共 60 次对比全部一致。
- iPhone 15 Pro 和 iPhone 11 上各 20 个脚本加 10 个基准，输出摘要与 Mac 全部一致。
- 过程中遇到的三处差异都是 toybox shell 自身的问题，在参考内核上同样出现：读端提前退出时写端挂住，查不到用户时读脏缓冲区，以及循环中的内存泄漏。最后一项在 1 GiB 的段里会耗尽地址，Mac 上改用 4 GiB，iPhone 上用 2 GiB。

**开销**（最好成绩，毫秒）：

### 用 AOSP 源码构建的 Bionic 客体

构建机是 Google Cloud 上的 n2-standard-32（Ubuntu 24.04）。源码是 `android-17.0.0_r1`，产品 `sdk_phone16k_arm64-cp2a-userdebug`，即 16 KiB 页的模拟器镜像。补丁和脚本在 `experiments/aosp`。

**要改的地方**（`experiments/aosp/patch.py`）：

| 位置 | 改动 |
| --- | --- |
| Soong 的 arm64 C/C++ 参数 | 加 `-ffixed-x18 -ffixed-x25 … -ffixed-x28` |
| Soong 的 arm64 Rust 参数 | 加 `+reserve-x18,+reserve-x25 … +reserve-x28` |
| Bionic `setjmp.S` | 不再就地混淆、保存和恢复 x25–x28 |
| Bionic 链接器 | 装载前用系统调用 0x4e56 询问宿主该文件的固定地址，真实内核上返回 ENOSYS 而不受影响 |
| BoringSSL | 加 `OPENSSL_NO_ASM`。它的汇编把 x25–x28 当工作寄存器 |
| ART | 代码生成器不分配 x25–x28，JNI 调用约定和快速编译器的寄存器表去掉它们，入口汇编不再恢复它们，nterp 暂时关闭 |

- **工具链自带的运行时库是预编译的**，必须重编：compiler-rt builtins、libunwind、libc++、libc++abi（`build-runtimes.sh`，按 `toolchain/llvm_android` 的配方）。重编后的 `libc++.so` 导出符号与原版只差一个性能剖析标记。
- 重编前 `libc.so` 有 311 条指令用到 x25–x28，`linker64` 有 3,173 条，全部来自这些预编译库。重编后分别是 6 条和 29 条：前者是 libunwind 保存和恢复上下文，后者是预编译的 ubsan 报错例程，还没有重编。
- ART 的补丁已经运行验证，见下面「在改写后的代码上运行 ART」。完整镜像的构建仍在进行，其他带手写汇编的库（如 TensorFlow Lite 的 ruy）会在这一轮里暴露出来。

**运行**（`experiments/g0/e3/build-android.sh`）：13 个模块各自按固定装载地址改写，链接成一个程序。运行时扮演内核装载可执行文件和 `linker64`，由 `linker64` 自己重定位并装载 11 个动态库。运行时为此补了信号投递（mksh 靠 SIGCHLD 回收子进程）、`/proc/self/fd` 的路径查询，以及在系统调用边界去掉 Bionic 堆指针最高字节的标签。

**正确性**（`compare-android.py`）：参考是同一批二进制在 ARM64 Linux 内核上 chroot 运行。

- Mac 上 19 个脚本的输出和退出码全部一致。
- iPhone 15 Pro（iOS 26.2）上 17 个一致。另外两个是 6–7 个进程的长管道，fork 失败：这个实验用的运行时给每个进程保留一整段 9 GiB（Scudo 一次要保留 8.25 GiB），超过了 53 GiB 的上限。这正是「地址保留和查表翻译」一节要解决的问题，不是改写的错误。

**开销**（最好成绩，毫秒）：

| 基准 | Linux 原生 | Mac 改写后 | 倍数 | iPhone 15 Pro |
| --- | --- | --- | --- | --- |
| sha256sum 251 MiB | 464 | 495 | 1.07 | 649 |
| wc 251 MiB | 181 | 207 | 1.14 | 323 |
| gzip 14 MiB | 184 | 211 | 1.15 | 287 |
| sed 200 万行 | 989 | 1,377 | 1.39 | 2,176 |
| grep 200 万行 | 237 | 305 | 1.29 | 602 |
| shell 循环 30 万次 | 284 | 352 | 1.24 | 595 |
| 300 次 fork | 475 | 744 | 1.56 | 1,452 |
| sort 200 万行 | 约 2,255 | 16,031 | 7.1 | 26,585 |

- 都是基址寄存器模式，返回地址保持为客体地址。sha256 是 C 实现，因为 BoringSSL 的汇编已关闭。

### 在改写后的代码上运行 ART

`build_guest.py` 把一棵 AOSP 构建产物目录（`system/`、`apex/`）整体改写：113 个模块，其中 9 个是启动镜像的 `boot*.oat`，共 2,637,560 条 AOT 指令。产物是一个 151 MB 的宿主程序和一个 175 MB 的客体根目录，`run-art.sh` 用它启动 `dalvikvm64`。

| 运行方式 | 结果 | Mac 上耗时 |
| --- | --- | --- |
| 无启动镜像，全部解释（`-Xint`） | Hello 输出正确，退出码 0 | 0.16 s |
| 装载启动镜像，托管代码仍解释 | 同上 | 0.04 s |
| 装载启动镜像，执行 AOT 代码 | 同上 | 0.04 s |

**iPhone 15 Pro（iOS 26.2）**上同一份产物装进探针应用（目标 `G0Art`，应用包 319 MB），三种方式的输出都正确，原始报告在 `g0-e3-art-iphone15pro-ios26.txt`：

| 运行方式 | 耗时（最好成绩） |
| --- | --- |
| 无启动镜像，全部解释 | 198 ms |
| 装载启动镜像，执行 AOT 代码 | 77 ms |

这是从 `execve` 到虚拟机退出的整个进程：装载 60 多个动态库、初始化运行时、映射启动镜像、运行 Hello、关闭虚拟机。每种方式的第一次运行要慢一些（解释方式 449 ms）。

- 测试程序 `guest-tests/Hello.java` 自身没有 oat，由解释器执行。启动类路径（核心库、framework、ICU）在第三种方式下执行 dex2oat 生成的机器码，包括编译出的 JNI 桩和抛异常时的栈遍历。
- 打过补丁的 dex2oat 生成的 `boot.oat` 里 x25–x28 的使用为 0（307,964 条指令）。
- oat 文件按它所属 `.art` 文件头里的 `oat_file_begin` 改写，运行时加 `-Xnorelocate`，ART 就把它映射到同一地址。
- oat 的膨胀率是 1.57–1.77，高于 C/C++ 模块，因为托管代码的调用几乎都是 `ldr x30, [x0, #24]; blr x30` 这样的间接调用，每次都要查表。`boot-framework.oat` 里间接调用占 7.7%，访存占 26.9%。

**为此修掉的问题**：

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 汇编 `boot-framework.oat` 时跳转超出范围 | 改写后代码变大，条件跳转和 `cbz` 只够得着 1 MiB | 距离超过 384 KiB 时改成「反条件跳过 + 无条件跳转」 |
| 启动镜像被拒绝：读屏障状态不一致 | 镜像按 userfaultfd GC（无读屏障）编译，运行时没有 `/proc/self/cmdline`，ART 读不到 `-Xgc:CMC` 而退回 CC | 运行时提供 `/proc/self/cmdline`，并指定 `-Xgc:CMC`。`userfaultfd` 仍未实现，ART 自动改用停顿式压缩 |
| 栈遍历找不到栈映射，返回地址落在别的 oat 里 | 其他 oat 里的代码用直接 `bl` 调用第一个 oat 里的 thunk（`boot-framework.oat` 有 12,141 处），改写器把模块外的直接跳转原样留下了 | 模块外的直接跳转改为查表 |
| 中止信息丢失 | 日志套接字的数据报上限是 2 KiB | 调大缓冲区 |

**还没做的**：`membarrier` 和 `userfaultfd` 两个系统调用（GC 因此走停顿式压缩，已验证能跑）；nterp（现在用 switch 解释器）；应用自身的 oat（需要在客体里跑 dex2oat 或在构建机上预编译）；iPhone 上只跑了 Hello，没有跑性能基准。

| 移除 Mach 端口后再走信号 | 100,000 | 全部 | 1.5 µs | 2.4 µs |

- 未映射地址报 SIGSEGV，保护错误报 SIGBUS，`si_addr` 都正确。两个信号都要处理。
- 评审中提到的「混用 Mach 异常端口后只有第一次恢复成功」在 iOS 26 上没有复现。
- 这是开发签名的 Release 构建。TestFlight 或 Ad Hoc 签名（无 `get-task-allow`）还没有验证。

## E5 签名代码装载

8 个 framework，每个 64 MiB 代码，App 共 514 MB。代码是随机生成的寄存器运算，每 4 KiB 一个以 `ret` 结尾的函数。

| 运行 | 设备 | dlopen 合计 | 首次触碰 512 MiB |
| --- | --- | --- | --- |
| 先弄脏 3,114 MiB 内存再测 | iPhone 15 Pro | 50 ms | 717 ms |
| 紧接着再次启动 | iPhone 15 Pro | 8 ms | 237 ms |
| 刚安装后 | iPhone 11 | 105 ms | 536 ms |
| 先弄脏 1,837 MiB 内存再测 | iPhone 11 | 88 ms | 1,365 ms |
| 紧接着再次启动 | iPhone 11 | 22 ms | 332 ms |

- 再次触碰 512 MiB 只要 16–28 ms，代码页不计入内存占用。
- 顺序执行全部冷代码约 0.8–1.07 GIPS，不代表热循环。
- iPhone 11「刚安装后」那一轮的原始报告被后一轮覆盖，数字取自当时的终端输出。重启后的真正冷启动没有测。安装包压缩后的体积也没有测，随机代码不具代表性。

## 由此定下的参数

- Extended Virtual Addressing 和 Increased Memory Limit 是必需权限。
- 客体内存按 16 MiB 的块查表翻译，不再给每个进程保留一整段。x25–x28 的分工相应调整，见 `rewrite.py`。
- 客体页大小与宿主一致时（16 KiB）映射和保护才能直接交给宿主。
- 子进程基址预先保留，fork 用写时复制重映射，共享文件映射逐个恢复共享。
- Zygote 的客体内存用文件后备的共享映射。
- SIGSEGV 和 SIGBUS 进程内恢复可用，dex2oat 不必改成显式检查。
- 翻译产物可以按 500 MiB 量级规划。
- 返回地址保持为客体地址的代价很小，可以直接采用，ART 的栈遍历不用改。

## 到 15 秒还差什么

现有运行时在 iPhone 15 Pro 上到 Launcher 要 606 秒，其中约 184 亿条客体指令由解释器执行。新路线各部分的状态：

| 部分 | 状态 |
| --- | --- |
| 代码改写（C/C++、Rust、ART 的 AOT 代码、JNI 桩） | 可用。Bionic 工具、多线程、信号、`dalvikvm` 加启动镜像都在 iPhone 15 Pro 上跑通 |
| 稀疏地址空间 | 可用，见「稀疏地址空间的实现」。多进程不再受每进程一整段的限制 |
| 保留寄存器的完整镜像 | 能完整构建，在参考模拟器里正常开机，原生速度下 6.8 秒到 Launcher（Mac，4 核） |
| 全量 AOT 的启动镜像和 system_server | 已在构建里打开，启动镜像已用于 zygote 的运行。system_server 的 odex 还没有接入改写 |
| Zygote | 在改写后的运行时上完整启动并进入等待循环，能 fork 出 system_server。预加载在 iPhone 15 Pro 上约 0.29 秒 |
| system_server | 进程起来后在打开 Binder 时终止，要等内核层接入 |
| Linux 内核层 | 没接。E3 的运行时只有约 110 个系统调用，没有 Binder、epoll、属性服务。现有运行时（`runtime/ProbeLinux.cpp`）有完整的一套，但它的内存模型是软件分段，要换成稀疏地址空间才能让原生代码直接访问 |
| 多核 | E3 里客体线程就是宿主线程。现有运行时是单线程调度，接入后要先用一把大锁，再逐步拆 |

两种估算：

- 按指令数：184 亿条指令，稀疏模式约为原生的 1.4–1.5 倍，假设原生单核每秒执行 30–40 亿条（这个数没有在本机实测），单核约 7–9 秒，前提是全部走 AOT 代码。
- 按原生基线：同一套镜像在 Mac 的虚拟机里 6.8 秒到 Launcher（4 核）。iPhone 15 Pro 在本文的基准里比这台 Mac 慢 1.3–1.4 倍（sha256 649 对 495 ms，zygote 预加载 111 对 78 ms），再乘改写的 1.4–1.5 倍，约 12–14 秒。这还没算内核层比 Linux 慢多少，而且手机只有 2 个性能核。

内核层的服务时间和等待在现有运行时里没有单独量过，接入后才能知道。所以 15 秒处在可达范围的边缘，是否达到取决于内核层移植后的实测，现在不能下结论。

## 内核层接入的做法

实验运行时到 Binder 为止。往下要让改写后的代码直接进现有运行时（`runtime/ProbeLinux.cpp`）的系统调用层，它已有 Binder、属性服务、ext4、图形管道。接入点和顺序：

1. **地址空间**：`runtime/GuestSpace` 是实验里验证过的稀疏地址空间，已抽成主运行时的组件，带宿主测试（`tools/validate-guest-space.cpp`）。每个客体进程一个，fork 时写时复制。
2. **段的存储**：内核层用 `Segment` 记录映射，内容放在几种存储里。原生执行要求内容就在 `GuestSpace` 给出的宿主地址上。做法是让 `AnonymousPages` 多一种由 `GuestSpace` 支撑的实现，私有映射（匿名、文件的私有副本）都走它，内核层通过 `Segment::data()`、`Machine::read/write` 的访问不用改；共享存储（`SharedFileBytes`，用于内存文件、ashmem、Binder 缓冲区）改成可共享的宿主内存并登记映射位置，增长时重映射；只读的镜像视图在镜像按 16 KiB 对齐后直接写时复制映射。
3. **页大小**：内核层的 `pageSize` 从 4096 改为 16384，根文件系统换成重编的镜像。
4. **执行**：先保持单线程调度。调度器选中一个客体线程后进入它的改写代码，到 `svc` 或故障回到调度器，时间片用信号打断。被打断的线程用信号返回的方式原样恢复（恢复路径不能占用 x28）。之后再把调度拆到多核。
5. **代码表**：按模块从程序文件直接映射进总表，不再复制。

已做的两步：

- `GuestSpace` 组件和它的宿主测试（22 项通过）。
- 用 `tools/prepare-init-root.py` 从运行重编镜像的模拟器采集启动输入（`generated/android17r-init-root`，909 MB），交给**现有的解释器运行时**跑 `tools/probe-init.sh`：原版 init 解析启动脚本、生成链接器配置、激活 Runtime APEX，并启动了 gatekeeper 和 keymint 等 HAL 进程，探针在 14 亿条指令的预算内没有遇到不支持的系统调用。重编镜像的二进制按 16 KiB 对齐，在内核层现有的 4 KiB 页语义下也能运行，所以换页大小和换执行方式可以分开做。

- 内核层的页大小成了构建参数（`NESTVANE_PAGE_SIZE`）。设为 16384 时同一个探针的各项验证结果与 4096 时相同。
- `AnonymousPages` 多了一种放在 `GuestSpace` 里的实现。设置 `NESTVANE_NATIVE_MEMORY` 后，每个进程有自己的地址空间，延迟分配的匿名映射和初始栈都在里面，fork 写时复制，`mremap` 和解除映射相应处理。解释器在这套内存上跑 init 探针，验证结果不变；默认模式下原有的宿主验证（`tools/validate-host.sh`）照常通过。

- 其余私有段（文件的私有副本、只读镜像视图、小的匿名映射、ELF 映像）在插入和拆分时也搬进 `GuestSpace`。同一个探针下内核层自己的私有缓冲区容量降为 0，验证结果不变。只读文件内容目前是复制进去的，之后要改成写时复制映射以免每个进程各占一份。

- 共享存储（内存文件、ashmem、BPF 映射等 `SharedFileBytes`）的字节在第一次被映射时搬到可共享的宿主页（`SharedBuffer`），按页映射进各进程的 `GuestSpace`；存储增长或搬动后重新映射，fork 后在子进程的地址空间里重新建立共享。地址、偏移或长度不按 16 KiB 对齐的共享段仍只由内核层访问。同一个探针连续 8 次运行，验证结果都与普通模式相同，`tools/validate-host.sh` 通过。

  接入时查出一个偶发的越界：页存储按 64 KiB 的块取连续指针，块从存储起点算，不一定落在一个 chunk 里，而相邻 chunk 可能属于不同的 run，中间隔着保护页。读指针现在不跨 chunk，跨界的读写走分段复制。是否出错取决于宿主分配到的地址，所以以前有时通过。

- **改写后的代码在内核层下原生执行**（`results/g0-native-init-mac.txt`）。`tools/build-native-code.py` 把启动输入里的 1050 个 ELF 按固定装载地址翻译并链接进探针；内核层把翻译过的可执行文件和链接器装在各自的地址上，用辅助向量里的表让链接器把库也装到位（文件第一次被 `fstat` 时登记），代码段映射到位后该进程的这段地址就原生执行。执行循环遇到这样的 pc 就进入原生代码，直到：
  - `svc`：回到内核层，由原有的系统调用实现处理；
  - 宿主故障（延迟分配的 chunk、未放进 `GuestSpace` 的段、跨 run 的访问、陷阱指令）：把寄存器交还，由解释器执行这一条客体指令，再回到原生代码。故障只发生在一条指令的访问处，那时客体寄存器还是指令执行前的值；
  - 时间片到：监视线程发信号，只在两条客体指令之间才生效，否则稍后重发；
  - 跳到没有翻译的地址，或程序入口（内核层要观察到进程到达入口）：表项是一个带标记的非法地址，故障地址给出客体 pc，改由解释器执行。

  Mac 上同一个探针程序：解释器 20.5 秒（14.1 亿条指令），原生 5.6 秒，其中 CPU 只有 0.8 秒，解释执行的指令降到 206 万条；十条验证结果相同，到达入口的 33 个进程相同，没有一次失控。

- **完整开机目录上的原生执行**（`results/g0-native-boot-mac.txt`）。`tools/prepare-boot-image.py --prebuilt-code` 用重编镜像自带的启动镜像和预编译产物组装带 Launcher、SystemUI 的开机目录；翻译 1222 个 ELF 文件，另加 608 份备用，共 1830 份、12 个动态库（单个 Mach-O 镜像装不下）。Mac 上没有图形后端，SurfaceFlinger 每次启动都因找不到 EGL 配置而中止并带着 zygote 重启，所以到不了 Launcher；到此为止的阶段：探针启动后 4.2 秒 SurfaceFlinger 启动，4.4 秒 zygote 开始预加载，完整的一轮预加载约 0.3 秒，system_server 在 zygote 开始预加载后约 0.6 秒进入、`InitBeforeStartServices` 181 毫秒。45 秒里 99 万次进入原生代码，没有失控。途中解决的问题：
  - **地址对齐**：Bionic 的 CFI 影子表每 256 KiB 一项，两个库不能落在同一项里，预链接地址按 256 KiB 对齐。64 KiB 对齐时 keymint 在 `__cfi_check` 里中止。
  - **同一内容的多个文件，同一文件的多次装载**：system 和 vendor 各有一份相同的 libc++，APEX 里还有 20 份；应用的类加载器命名空间会把非公开的平台库再装一遍；system_server 会把 zygote 已装载的 odex 再装一遍。一份翻译只对应一个地址，所以每个路径各翻译一份，平台库和 framework 的 odex 再各留一份备用，内核层在进程里按"还没用过的那一份"分配，文件装到位后把表里的地址换成下一份。
  - **inode 号不能当文件身份**：内核层的 inode 号会换给别的文件，预链接按文件内容判断。
  - **启动镜像不重定位**：`dalvik.vm.extra-opts=-Xnorelocate`，否则 zygote 把 boot.oat 装到随机地址。
  - **`mremap` 搬页**：CMC 回收器用 `MREMAP_FIXED|MREMAP_DONTUNMAP` 把 96 MiB 的堆搬开，原实现先复制到临时存储，超出预算；在 `GuestSpace` 里改为直接搬页。
  - **安全网**：进程里只要有没装到位的可执行映射，或者程序本身没有翻译，整个进程退回解释执行。原生代码调用未翻译的代码时查表会越界，退回解释器最稳妥。
  - **BPF 加载器**：`tools/build-netbpfload.py` 在仓库目录里运行时 `git apply` 会静默跳过补丁，生成的是未打补丁的加载器，netd 因此中止并带着 zygote 重启。已修，并让它带保留寄存器编译。

还没接的：Binder 缓冲区和未对齐的共享映射，按客体权限设置宿主页保护，多核调度，以及代码表按需复制之外的启动开销。iPhone 上的 App 目标（`nestvane-native`，`tools/prepare-ios-native.sh`）已加进工程，还没有上机运行；到 Launcher 还需要 iOS 的 gfxstream 和 ANGLE 框架，这台 Mac 上没有它们的构建产物。
